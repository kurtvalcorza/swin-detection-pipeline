## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, repository import, worker process or subprocess (the generator-owned install cell excepted). Section 2 carries `src/dimer_swin_detection/metrics.py` and `src/dimer_swin_detection/runtime.py` verbatim, in dependency order (each tagged `metadata.dimer.embedded_module`; the rewrites make the default weights directory working-directory-relative and drop the one package-relative import), Section 3 carries the model identity and the 1-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `tools/pins.txt` runtime pins including the PyTorch CPU index and the OpenMMLab mmcv find-links. `metadata.dimer.generated_from` records the repository, the generating revision, both module paths, their joined SHA-256, and the generator version.
- **Qualified runtime (ENV2/ENV4):** CPython 3.10 with torch 2.1.2+cpu, MMCV 2.1.0, MMEngine 0.10.7, MMDetection 3.3.0, NumPy 1.26.4, pycocotools 2.0.11. `pip` cannot pin the interpreter, so Section 1 builds an isolated environment with a uv-managed CPython 3.10.18 (exact version checked) and the exact pins of `tools/pins.txt` (in `dimer_isolated_env/`, or the folder named by the `DIMER_ISOLATED_ENV` environment variable), and routes every later cell to it; Section 4 asserts `sys.version_info[:2] == (3, 10)` there, and the carried `verify_runtime_versions` fails closed on OpenMMLab version drift. The kernel's own Python no longer matters; a Colab CLI T4 run of the previous blob is recorded, and the current revision's hosted run is pending.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when a carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition and trust boundary (MOD12–MOD14):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the absent checkpoint from the pinned `download.openmmlab.com` URL (the manifest's single entry; the model host is not the Hugging Face Hub and the `MODEL_REVISION` is the MMDetection `v3.3.0` release-tag commit that is the config source); `verify_snapshot` re-hashes it against the manifest **and** `MODEL_SPEC`; `from_pretrained(weights_dir=WEIGHTS_DIR)` then lets the pinned MMDetection loader deserialize the code-capable `.pth` (upstream's `mmengine` load, not `weights_only`). The notebook states that the digest proves byte identity, not publisher authenticity.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/swin_detection_task_inference_input_manifest.json` with the schema, ceilings (`MAX_PIXELS` 64,000,000; `score_threshold` 0..1; `max_detections` ≥ 1), per-input observations, verdict, and one recorded rejection finding (missing-file probe); `evaluation_report` (EVAL21) writes `outputs/swin_detection_task_inference_evaluation_report.json` — `sample-sanity` with `coco_box_ap` (COCO AP@[0.50:0.95], AP50, AP75 via pycocotools; top 100 detections per image) and the empty-detector baseline on the default val2017 sample, with a `training_overlap` field (`eval_data_in_training: false`), and `not-measurable` on the optional synthetic scene (with what labelled data would make the task measurable). Every report is written atomically (temporary file, then rename).
- **Samples:** the default sample is 50 COCO val2017 images chosen by a fixed rule before any score was seen (licence CC BY 2.0, CC BY-SA 2.0, no known copyright restrictions or US Government work; at least one non-crowd box and no crowd box; no train2017 match by image id, Flickr photo id or (width, height, capture time); first 50 by image id). They are mirrored as assets of release [`data-coco-val2017-50-v1`](https://github.com/kurtvalcorza/swin-detection-pipeline/releases/tag/data-coco-val2017-50-v1) with `ATTRIBUTION.md` (per-image licence, Flickr source and COCO URL; COCO does not record photographers' names) and the pin `coco_val2017_sample_50.json` (also at `tools/`); the notebook downloads each image from the release and refuses it unless its SHA-256 matches, and checks the inline ground truth (279 boxes) against its digest. `images.cocodataset.org` is recorded for provenance only. The checkpoint was trained on train2017; val2017 is the split upstream reported box AP 42.7 on and may have used for model selection, so the result is a sanity measurement, not an independent test. `SAMPLE = 'synthetic'` draws a deterministic 640×480 scene in code (no download, no ground truth).
- Detection obligations: the class count (80) and request ceilings are printed before the model runs, scores are described as uncalibrated MMDetection confidences with no shipped threshold (`score_threshold` is a caller-owned output filter, 0.0 for evaluation), and exported detections keep their score ordering per image in both JSON and CSV.
- `USE_BYOD` defaults to `False`, so the default path never opens an upload dialog. A BYOD input the cell cannot use is refused with one message naming the file and the rule; earlier exploratory outputs move to `outputs/earlier_<n>/` (the default sample's files stay in place) and Sections 6–9 skip. Uploads are saved under `sample/byod/`, so they never overwrite a pinned sample image.
- **Filename (NOTEBOOK_SPEC 2.5 KND2, recorded deviation):** the kind is `TUTORIAL`, whose recommended pattern is `<model>_<task>_colab.ipynb`. The file keeps the name `swin_detection_task_inference.ipynb` so existing Colab links, CI paths and the validator keep working; KND2 is a SHOULD. A rename is a separate decision for the maintainer.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`. Earlier records (the Notebook Specification 1.0 run of 2026-09-11 and the Colab T4 run of blob `ea6b456d`, both AP 0.707 on four COCO8 train2017 images) are kept there as an audit trail; they are resubstitution scores, not measurements.
